Phase 3: Root Cause Analysis

Two distinct hardware and software bottlenecks, happening sequentially, were responsible for the 30-second delay.

1

Database & Compute Bottleneck

+29,990 ms

The 29.99-second load time for the initial HTML document means the origin server is hanging. The monolithic WordPress/Elementor architecture forces the server to execute heavy, unoptimised PHP and query the MySQL database from scratch for every single incoming connection — producing the page dynamically every time.

My Client — Dynamic Rendering
  • WordPress + Elementor (monolithic stack)
  • PHP executes on every request
  • MySQL queried cold — no cache layer
  • TTFB: ~29,990 ms
Competitor — Server-Side Cache
  • Pre-compiled flat HTML files served instantly
  • Zero real-time database computation
  • Edge-cached HTML delivered globally
  • TTFB: ~1,350 ms

After HTML loads, next bottleneck hits:

2

Network Pipeline Saturation

~70 MB VIDEO

Immediately after the server finally delivers the DOM, the application forces the browser to download roughly 70 MB of MP4 video chunks as a background hero. Browsers enforce a hard limit on concurrent connections — these massive video chunks saturate the bandwidth pipe, causing critical downstream assets (CSS and JS) to enter a Stalled state for up to 30 additional seconds.

My Client — Auto-play MP4 Hero
  • 70 MB MP4 loaded on initial paint
  • Saturates all browser concurrent connections
  • CSS/JS enter "Stalled" state — render blocked
  • Secondary delay: +30 seconds
Competitor — Modern WebP Hero
  • Single WebP image for initial viewport
  • Only 60.4 kB transferred (vs 70 MB)
  • Zero bandwidth saturation — pipeline free
  • All structural code executes instantly

Phase 4: Engineering Action Items

The prescribed remediation, formatted as sprint-ready engineering tickets to achieve parity with the benchmark architecture.

TICKET-001 / HIGH PRIORITY

Implement Server-Side Page Caching

TTFB Target
30,000 ms → <1,000 ms

Deploy a caching layer to store fully compiled HTML documents. The server will serve pre-rendered pages from memory instead of hitting the database on every request.

Redis
In-memory key-value store
Memcached
High-performance object cache
Edge Cache (CDN)
Cloudflare / Fastly layer
Expected Outcome: TTFB drops from 30,000 ms to under 1,000 ms. The server now skips PHP execution and MySQL queries entirely for cached pages, serving static HTML at memory speed.

TICKET-002 / HIGH PRIORITY

Halt Auto-Loading Media on Initial Paint

Payload Reduction
70 MB → <100 KB

The background MP4 must not execute during initial DOM construction. Two viable engineering paths:

▶ OPTION A — Recommended

Replace with WebP / AVIF Animation

Convert the video to a highly compressed looping WebP or AVIF animation. A 10-second visual loop can be under 200 KB vs 70 MB.

Zero JS required 99.7% smaller
▶ OPTION B — If Video is Mandatory

Defer Video with JS

Inject preload="none" and a static poster image. Use JS to trigger download only after window.onload fires.

<video
  preload="none"
  poster="hero-still.webp"
  id="hero-video"
></video>
// Deferred in JS:
window.onload = () => {
  v.src = 'hero.mp4'; v.play();
};
Expected Outcome: CSS and JS files are no longer "Stalled" by video chunk downloads. Critical Rendering Path is cleared, reducing total scripts complete from 15.8s to under 3s.
